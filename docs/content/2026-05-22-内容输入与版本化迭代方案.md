# 内容输入与版本化迭代方案

本文用于指导「异界开局人格测试 / 游戏人格 H5」后续正式题库、人格结果和分享文案输入后的开发接入、版本管理与验收。

当前 GPTI 第一批短文案主要用于验证答题流程、结果映射、分享链路、埋点采集、rollup 和 dashboard 兼容口径，不代表最终上线内容。

> 2026-05-23 更新：项目已正式迁移到 GPTI 新体系。本文中的版本管理、改动分级、接入流程、看板口径和回滚原则仍适用；旧 `EI/SN/TF/JP`、左右选项、`INTJ` 示例只作为 `content-2026-05-21` 历史样稿说明保留。当前题库、结果和隐藏特质输入模板以 `2026-05-23-GPTI内容输入模板与校验规则.md` 为准。

## 1. 目标

后续文案组给出正式内容后，开发侧应尽量只替换内容配置，不改业务逻辑。

核心目标：

- 支持题库、章节反馈、人格结果、分享文案和视觉资产持续迭代。
- 每次影响用户理解、选择或传播的数据变更都能通过 `contentVersion` 区分。
- 保持埋点、rollup、dashboard 在不同内容版本之间可对比、可追溯。
- 避免内容大改时误改打分逻辑、结果结构或数据看板口径。

## 2. 当前内容边界

当前内容配置文件：

```text
src/data/gpti.mjs
src/data/questions.mjs
src/data/results.mjs
src/data/traits.mjs
```

当前内容版本声明位置：

```text
index.html
src/app.mjs
docs/content/2026-05-23-GPTI内容输入模板与校验规则.md
```

当前技术结构默认：

- 24 道题。
- GPTI 四选项题库，每个选项包含用户可见文案、关键词和八极 `poles` 分值。
- 4 个 GPTI 轴：`A/P`、`T/I`、`R/W`、`B/C`。
- 标准 16 型 GPTI key：`ATRB`、`ATRC` 等 16 个内部结果 key。
- 隐藏特质 / 稀有变体作为附加展示，不覆盖标准 16 型主结果。

这些结构当前服务于 GPTI 第一版基础链路验证。正式内容落地时，若仍沿用 GPTI 第一版结构，应优先走低风险内容替换流程；若改变题量、评分结构、主结果体系或看板口径，需要先更新 spec、测试和实现方案。

## 3. 内容输入模板

建议文案源统一维护在腾讯文档。开发接入前，文案应整理为结构化表格，避免直接从长文中手工复制。

### 3.1 GPTI 题库输入表

当前 GPTI 题库输入字段以 `2026-05-23-GPTI内容输入模板与校验规则.md` 为准。核心字段包括 `id`、`chapter`、`title`、四个选项的 `text`、`keywords` 和 `poles`，选项 id 使用 `a` / `b` / `c` / `d`，不再使用旧 `dimension`、`weight`、`leftChoice`、`rightChoice`。

### 3.1.1 历史旧样稿题库输入表

| 字段 | 说明 | 必填 | 示例 |
|---|---|---:|---|
| `id` | 题目 ID，保持 `q01` 到 `q24` | 是 | `q01` |
| `chapter` | 章节编号 | 是 | `1` |
| `chapterTitle` | 章节标题 | 是 | `坠入异界` |
| `chapterFeedback` | 完成本章节后的反馈文案 | 是 | `你的开局方式已经被记录。` |
| `dimension` | 打分维度 | 是 | `EI` |
| `weight` | 权重 | 是 | `1` |
| `title` | 题干 | 是 | 用户看到的题目 |
| `leftChoice` | 左侧选项文案 | 是 | 偏左侧字母倾向 |
| `rightChoice` | 右侧选项文案 | 是 | 偏右侧字母倾向 |
| `notes` | 文案备注、风险或争议点 | 否 | 待复审 |
| `status` | 文案状态 | 是 | 草稿 / 待审 / 已确认 |

输入要求：

- `id` 不重复。
- `title`、`leftChoice`、`rightChoice` 不为空。
- 同一个维度下题目数量保持一致，除非本轮明确要改打分结构。
- 选项文案应互斥，避免两个选项实际表达同一倾向。
- 避免现实身份、职业、地域、性别或具体群体攻击。

### 3.2 GPTI 结果输入表

当前 GPTI 结果输入字段以 `2026-05-23-GPTI内容输入模板与校验规则.md` 为准。核心字段包括 `type`、`name`、`identity`、`headline`、`tags`、`summary`、`behaviorFragments`、`charges`、`talent`、`weakness`、`bestPartners`、`nemesis`、`shareCTA` 和可选 `longCopy`。用户端默认不展示 `ATRB` / `ATRC` 等内部 type code。

### 3.2.1 历史旧样稿人格结果输入表

| 字段 | 说明 | 必填 | 示例 |
|---|---|---:|---|
| `type` | 内部结果 key | 是 | `INTJ` |
| `name` | 用户可见结果名 | 是 | `PLAN-B 预案怪` |
| `identity` | 用户可见身份或档案类型 | 是 | `终局策士` |
| `headline` | 结果页核心判词 | 是 | 一句话主文案 |
| `worldCopy` | 异界身份解释 | 是 | 世界观视角文案 |
| `playerCopy` | 玩家视角解释 | 是 | 玩家视角文案 |
| `tags` | 结果标签数组 | 是 | `预判,复盘,战略` |
| `charges` | 系统罪状数组 | 是 | 3 条左右 |
| `talent` | 隐藏天赋 | 是 | 一句话 |
| `weakness` | 致命弱点 | 是 | 一句话 |
| `bestPartners` | 适配队友数组 | 是 | 1 到 3 个 |
| `nemesis` | 天敌队友数组 | 是 | 1 到 3 个 |
| `shareCTA` | 分享行动文案 | 是 | 一句话 |
| `image` | 结果图资产路径或需求 | 否 | `./assets/results/INTJ.png` |
| `avatar` | 头像资产路径或需求 | 否 | `./assets/avatars/INTJ.png` |
| `notes` | 文案备注、风险或争议点 | 否 | 待复审 |
| `status` | 文案状态 | 是 | 草稿 / 待审 / 已确认 |

输入要求：

- 16 个 `type` 必须完整，除非本轮明确要改变人格体系。
- 用户可见文案中不直接展示内部 type code。
- `tags`、`charges`、`bestPartners`、`nemesis` 以数组形式交付，避免开发侧再拆句。
- 分享文案需要单独检查传播语气，避免过长或过度攻击性表达。

### 3.3 内容改动记录表

每次内容输入或修改建议记录：

| 字段 | 说明 |
|---|---|
| 修改日期 | 例如 `2026-05-22` |
| 修改批次 | 例如 `正式题库初稿 A` |
| 修改范围 | 题库 / 结果 / 分享 / 视觉资产 |
| 是否影响打分 | 是 / 否 |
| 是否影响结果映射 | 是 / 否 |
| 是否需要递增 `contentVersion` | 是 / 否 |
| 对比基准版本 | 例如 `content-2026-05-21` |
| 新内容版本 | 例如 `content-2026-06-01-a` |
| 文案负责人 | 姓名或小组 |
| 开发接入人 | 姓名 |
| 验收人 | 姓名 |
| 备注 | 风险、争议或回滚说明 |

## 4. 改动分级

### 4.1 低风险改动

低风险改动通常可以直接替换内容配置：

- 修改题干。
- 修改选项文案。
- 修改章节标题或章节反馈。
- 修改结果名称、身份、判词、解释、标签、罪状、天赋、弱点、队友和分享 CTA。
- 替换结果图、头像、分享图等视觉资产，但不改变文件结构。

低风险改动要求：

- 递增 `contentVersion`，除非只是错别字且不影响语义。
- 跑内容校验、测试和构建。
- 用真实浏览器检查排版、换行和分享表现。

### 4.2 中风险改动

中风险改动需要回归测试和人工验收：

- 调整题目顺序。
- 调整题目所属章节。
- 调整题目选项的关键词或八极 `poles` 分值。
- 大量重写题目，导致旧版本与新版本数据不能直接比较。

中风险改动要求：

- 必须递增 `contentVersion`。
- 在内容改动记录表中标注旧版本数据与新版本数据不可直接混算。
- 检查 dashboard 中按 `contentVersion` 筛选后的 summary、funnel、questions、results、share 口径。

### 4.3 高风险改动

高风险改动不能直接在内容配置中硬改，需要先更新 spec：

- 题目数量不再是 24。
- GPTI 四选项、关键词或八极 `poles` 结构发生变化。
- GPTI 4 轴或 16 个标准主结果 key 发生变化。
- 隐藏特质开始覆盖主结果，或增加动态稀有度 / 用户分位数判定。
- 增加并列结果、概率结果、标签型结果、稀有度动态计算或二级人格。
- 需要改变埋点事件结构、dashboard 统计口径或 rollup 聚合逻辑。

高风险改动要求：

- 先新增或更新 `specs/` 下对应 requirements、design、tasks。
- 明确新的数据结构、打分逻辑、结果映射和看板口径。
- 补充或重写测试。
- 经确认后再进入实现。

## 5. 开发接入流程

正式文案进入开发时，建议按以下步骤执行。

### 5.1 接收内容

开发侧先确认：

- 文案是否已在腾讯文档中标记为“已确认”。
- 题库表、结果表、改动记录表是否齐全。
- 本轮是否只改内容，还是会影响结构、打分或看板口径。
- 本轮应使用的新 `contentVersion`。

### 5.2 结构化整理

将文案整理成可写入代码的数据结构：

- 章节信息写入 `chapters`。
- 题库写入 `questions`。
- 人格结果写入 `results`。
- 数组字段保持数组，不在页面层拆字符串。

开发侧不应在接入时擅自改写文案含义。若发现过长、排版风险或表达冲突，应回到文案源确认。

### 5.3 替换配置

优先修改：

```text
src/data/questions.mjs
src/data/results.mjs
```

如本轮影响用户答题、结果理解或分享传播，同步修改：

```text
index.html
src/app.mjs
docs/content/2026-05-23-GPTI内容输入模板与校验规则.md
```

### 5.4 更新版本

推荐命名：

```text
content-YYYY-MM-DD-gpti-a
content-YYYY-MM-DD-gpti-b
```

示例：

```text
content-2026-06-01-gpti-a
```

同一天多次可见内容变更时，递增末尾字母。不要复用已经产生线上或验证数据的 `contentVersion`。

### 5.5 验收

在 `H5/demo` 目录运行：

```powershell
node --test .\tests\*.test.mjs
npm run build
```

真实浏览器检查：

- 首页标题、副标题、按钮文案正常显示。
- 24 道题均可进入和选择。
- 选项文案在移动端不溢出、不遮挡。
- 章节反馈正常显示。
- 结果页所有字段正常显示。
- 结果页不暴露内部 type code。
- 分享按钮、复制链接、分享图相关文案正常。
- 埋点事件中的 `contentVersion` 是新版本。
- dashboard 可按新 `contentVersion` 筛选。

## 6. 数据与看板要求

内容变化会影响用户选择、漏斗和结果分布。后续分析时必须区分版本：

- 不同 `contentVersion` 的结果分布不应直接混合解读。
- 正式上线前验证数据与真实运营数据应分开说明。
- 带 `host`、`origin`、`contentVersion` 筛选时，dashboard 的 summary、funnel、questions、results、share 需要保持同一来源口径。

禁止事项：

- `admin/dashboard.html` 直接读取 `analytics_events`。
- `dashboard_api` 请求时扫描 `analytics_events`。
- 把 dashboard token、密钥或敏感信息写入前端代码、仓库或腾讯文档。

## 7. 回滚方案

若正式内容上线后发现问题：

1. 判断问题类型：错别字、排版、结果映射、打分逻辑、数据口径。
2. 低风险文案问题可新建补丁版本，例如 `content-2026-06-01-b`。
3. 若涉及打分或结果映射错误，应停止继续投放该入口，回滚到上一版静态资源或重新部署修复版本。
4. dashboard 分析时保留异常版本，不删除数据，但在运营记录中标注异常原因。

回滚时不要复用旧版本号伪装成新内容。可重新部署旧内容，但需要在记录中说明实际回滚版本。

## 8. 协作分工

建议分工：

- 文案组：维护题库表、结果表和改动记录表，确认文案状态。
- 开发侧：负责结构化接入、版本递增、测试、构建和真实浏览器验证。
- 数据侧或开发侧：确认埋点、rollup、dashboard 口径。
- 项目负责人：确认正式内容进入预览或上线入口。

## 9. 当前建议

在题库和人格正式敲定前，继续将当前项目视为 GPTI 第一版技术链路版本。后续优先让文案源按 GPTI 模板交付，再根据第一版正式文案走一次完整的内容接入演练，并使用新的 `contentVersion`。
